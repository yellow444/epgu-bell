# Примеры подключения и дальнейшей автоматизации

Примеры относятся к получателю выходного JSON Bell. Исходный код сборщика,
вход на сайт, работа с сессией, контейнерные рецепты и методы извлечения
данных здесь не используются. Примеры включены в rc.4; старый опубликованный rc.3 автоматически не меняется.

## Что можно собрать

| Система | Первый полезный шаг | Дальнейшая обработка | Статус примера |
| --- | --- | --- | --- |
| 1С | Входящий регистр уведомлений | Задача ответственному, ручная привязка к документу, журнал проверок | BSL-пример есть, на платформе не запускался |
| Битрикс24 | Карточка смарт-процесса «Входящие уведомления» | Ответственный, очередь разбора, ссылка на проверенную карточку дела | Формирование REST-параметров проверено на mocks; облачный портал не подключался |
| n8n / Node-RED | Входящий webhook с ключом события | Ветка по категории, задача оператору, вызов согласованного получателя | Подготовка JSON проверена; импортируемого workflow и живой приемки нет |
| ServiceDesk | Входящая карточка на разбор | Привязка к клиенту после проверки, эскалация, учет времени реакции | Универсальный webhook-пример; конкретная система не подключалась |
| Telegram / почта | Краткое сообщение «есть новое уведомление» | Дайджест ответственному со ссылкой на вашу внутреннюю систему | Генератор обычного текста, без фактической отправки |
| SQL / BI | Копия локального inbox | Графики категорий и времени реакции | Проверенный SQLite-клиент; готового отчета BI нет |
| Оркестратор API/MCP | Карточка задачи с предложением проверки | Человек выбирает действие, затем формируется и одобряется план | Полный цикл ФССП пока воспроизводится на mocks |

Текст уведомления сам по себе не подтверждает статус услуги, срок или
соответствие конкретному делу. Примеры не закрывают дела и не подают
заявления по ключевым словам в тексте.

## Подготовить примеры без внешних подключений

Нужен Python 3.11+. Команды выполняются из корня репозитория документации.
Значения 128 и 7 ниже синтетические: это пример типа CRM и ответственного,
не реальные настройки портала.

```powershell
$automationRoot = Join-Path $env:TEMP ('bell-automation-' + [guid]::NewGuid().ToString('N'))
python examples/automation/prepare_actions.py --snapshot examples/snapshot.mock.json --db "$automationRoot/inbox.sqlite3" --output "$automationRoot/actions.json" --organization-id ORG-DEMO --connection-id demo --contour test --targets bitrix24,webhook,digest --entity-type-id 128 --assigned-by-id 7
python examples/automation/prepare_actions.py --snapshot examples/snapshot.mock.json --db "$automationRoot/inbox.sqlite3" --output "$automationRoot/actions.json" --organization-id ORG-DEMO --connection-id demo --contour test --targets bitrix24,webhook,digest --entity-type-id 128 --assigned-by-id 7
```

Первый запуск подготавливает 6 действий: два синтетических уведомления
для трех получателей. Второй добавляет 0, всего остается 6. Изменение
записи обновляет ее заготовки с теми же ключами. Это локальная подготовка,
а не создание карточек во внешних системах: в примере нет сетевого
исполнителя, адресов получателей и учетных данных. `delivery=disabled`
и `requires_operator_review=true` сохраняются в результате.

По умолчанию в заготовках нет заголовка и тела уведомления, только минимум
метаданных и нейтральный текст. `--include-text` явно добавляет текст
в выходной файл. Такой файл уже содержит сообщения; его нельзя класть
в публичный Git или пересылать в общий чат. Локальная SQLite импорта
также содержит тексты и требует обычной защиты пользовательских данных.

Параметры получателей закрепляются за этой базой. Для другой организации
или другого набора настроек используйте отдельную базу. Изменение настроек
существующей базы отвергается, а не молча меняет назначения подготовленных действий.

## Битрикс24: смарт-процесс входящих

В своем тестовом портале создайте смарт-процесс и выберите ответственного.
Его `entityTypeId` и идентификатор сотрудника подставляются в генератор.
Сначала проверьте доступные поля своего типа методом
[`crm.item.fields`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-fields.html).

Для каждой записи формируются два описания вызова:

1. [`crm.item.list`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html)
   с фильтром по внешнему `xmlId`.
2. [`crm.item.add`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html)
   с `entityTypeId`, заголовком, `xmlId` и `assignedById`, если карточки еще нет.

Внешний ID определяется подключением, контуром и ID уведомления. Сохраните
полученный CRM ID в своей таблице соответствий. При повторной обработке
обновляйте найденную карточку, а не создавайте новую. Смена ответственного,
стадий и дополнительных полей требует своего согласованного отображения.

Пара «найти, затем создать» не обеспечивает exactly-once при параллельных
исполнителях или потере ответа. В своем отправителе нужны сериализация
по ключу, журнал исхода и сверка результата после неоднозначного сбоя.
Сам `xmlId` не следует считать обещанием уникальности на стороне CRM.

Это пример для Битрикс24 CRM. Сайт на «1С-Битрикс: Управление сайтом» имеет
другой контекст интеграции; готовый модуль для него не поставляется.

## n8n или Node-RED: входящие события

В своем тестовом экземпляре настройте POST Webhook с аутентификацией.
У n8n разные test и production URL; используйте адрес из интерфейса,
а не придуманный URL. Описание параметров есть в
[документации Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/).

Генератор создает тело `bell-event-1` с `event_key` и `notification`.
Идентичное значение задается для заголовка Idempotency-Key. В будущем
отправителе подставляется только адрес вашего получателя; сессию Госуслуг
и локальный токен Bell передавать туда не требуется.

Предлагаемая последовательность узлов: Webhook, проверка структуры,
сохранение события с UNIQUE event_key, выбор очереди по категории,
создание задачи оператору. Если событие уже было, верните квитанцию
повторного приема. Подтверждение доставки должно следовать после
надежного сохранения. Конкретный workflow n8n/Node-RED этим примером
не развертывается и в живом экземпляре пока не проверен.

## 1С и ServiceDesk: входящие, затем бизнес-действие

Для 1С начните с [BSL-примера](../examples/1c/BellReader.bsl): он возвращает
таблицу. В собственной конфигурации можно добавить регистр входящих,
поле ответственного и отметку «проверено оператором». Ключ включает
подключение, организацию, контур и ID. Повторный прием должен обновлять
запись; старое наблюдение не должно откатывать новое.

В ServiceDesk используется тот же принцип. Сначала входящее событие,
затем проверенная связь с обращением. Равенство названий не является
достаточным основанием привязать уведомление к чужому делу. Автоматическую
эскалацию по времени реакции можно строить по собственным first_seen/last_seen,
не выдавая их за официальный срок ведомства.

## Краткое оповещение вместо пересылки документа

Заготовка digest содержит обычный текст без HTML или Markdown-команд.
По умолчанию это только «есть новое уведомление» и его локальный ID.
В своем отправителе можно выбрать почту или чат ответственного. Для Telegram
метод [`sendMessage`](https://core.telegram.org/bots/api#sendmessage)
принимает текст; без явного parse_mode он не интерпретируется как HTML/Markdown.
Учетных данных бота и фактической отправки в примере нет.

Для группы из нескольких сотрудников лучше давать ссылку на свою систему
с проверкой доступа. Не помещайте тело персонального уведомления в общую
рассылку по умолчанию. Подготовленный digest не является подтверждением доставки.

## Последующее действие через API и MCP

Пример связи: событие появляется во входящих Битрикс24 или 1С, оператор
проверяет источник и выбирает подходящую форму. Только после этого
создается план операции через ваш API. Одобрение остается отдельным
действием человека; MCP не получает право одобрить собственный план.

В публичном EPGU воспроизводимый полный цикл ФССП сейчас доступен на mocks.
Универсального автоматического преобразования любого уведомления в
боевую подачу или подтвержденный статус услуги эти примеры не обещают.
