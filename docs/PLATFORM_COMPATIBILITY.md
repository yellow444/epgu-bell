# Bell: вход, изменения платформ и границы готовности

Редакция документации: 26 ноября 2026 года. Бинарная поставка остается
0.2.0-rc.4; изменение этого документа не пересобирает образ и не меняет
состав уже опубликованного ZIP.

## Что делает Free самостоятельно

Одна установка относится к одной организации и контуру. Она читает
уведомления выбранного представления портала, сохраняет JSON/Base64 и SQLite,
устраняет дубли и предоставляет локальный HTTP API. Приватные исходники и
Multi для работы готового Free-пакета не требуются.

Публичный `examples/check_single_org.py` проверяет этот цикл на синтетических
данных, включая headless Demo, импорт, две страницы API и повтор без дублей.
Проверка использует новый отдельный каталог и останавливает собственный
контейнер. Запуск описан в [README](../README.md).

| Состав | Публичная поставка |
| --- | --- |
| Приложение Free | Бесплатная готовая сборка, исходники закрыты |
| Документация, JSON-контракт, проверка и клиенты | Публичный репозиторий |
| Чтение и накопление данных одной организации | В Free |
| Несколько организаций в одном управляющем запуске | Отдельный закрытый Multi |
| Несколько сотрудников с независимыми ролями в одном API | Не является принятой возможностью Free |
| Автоматический вход, подтверждение MFA, продление любой сессии | Не приняты |

## Как связан вход физлица с организацией

Пользователь входит в портал и выбирает нужную организацию. Bell получает
подготовленную пользовательскую сессию и должен подтвердить именно контекст
настроенной организации. Возможность входа физлица сама по себе не доказывает,
что текущая страница принадлежит нужному ЮЛ.

Проверки перед сбором:

1. OID и контур в конфигурации совпадают с выбранной организацией.
2. Сессия действует и имеет доступ к этому представлению портала.
3. Ответ источника подтверждает контекст; неизвестный контекст не принимается
   как успешный сбор пустой ленты.
4. При ошибке входа требуется действие пользователя; старые накопленные записи
   сохраняются. Нельзя подменять контекст, отключать проверки или считать ошибку
   сессии отсутствием уведомлений.

Для подготовки сессии используйте [SESSION.md](SESSION.md). Файлы сессии и
базы содержат чувствительные данные, в Git они не помещаются.

## Три разных вида доступа

- Сессия браузера дает пользователю доступ к странице в рамках его прав.
- Токен локального API Bell дает доступ к данным единственной установки Bell.
- API-Key ЕПГУ и маркер организации нужны для официальных услуг API ЕПГУ.

Эти значения не взаимозаменяемы. Bell не требует API-Key ЕПГУ для чтения
поддержанного представления через пользовательскую сессию. Наличие такой
сессии не подключает организацию к услугам API ЕПГУ и не выдает право подписи.

## Требования ЕСИА и переход к 2027 году

Письмо Минцифры от 08.10.2025 № ОК-П24-97784 устанавливает переход ранее
подключенных OAuth/OIDC-систем на требования приложения Д до 1 января 2027
года. Новое прямое подключение должно соответствовать требованиям при
подключении. В письме указаны защита канала, криптосредства соответствующего
класса и оценка влияния технического решения; предусмотрен перечень типовых
решений.

Bell использует предоставленную пользовательскую сессию и не становится от
этого зарегистрированным OAuth-клиентом, аттестованной ИС или типовым решением
ЕСИА. Для конкретного внедрения нужно определить его действительную схему
и применимость требований с оператором. Прошедший Demo или установленный
криптопровайдер не подтверждают соответствие всей системы.

Источники: [первичное письмо Минцифры](https://naufor.ru/download/2026/MZ_08102025.pdf),
[публикация Банка России через НАУФОР](https://naufor.ru/tree.asp?n=31662).

## Коммерческий вход через ЕСИА до 2030 года

Эксперимент для коммерческих ресурсов продлен до 31 декабря 2030 года.
Подключение конкретного сайта и права на данные согласуются отдельно.
Продление эксперимента не является разрешением на автоматический вход,
чтение произвольных кабинетов или обход проверок контекста Bell.

Источник: [официальное разъяснение прокуратуры](https://epp.genproc.gov.ru/ru/proc_42/activity/legal-education/explain/e8723161/).

## Интеграции и границы данных

- [Python-клиент](../examples/integrations/import_notifications.py) читает
  сохраненные записи и локальный API с пагинацией.
- [1С](../examples/1c/BellReader.bsl) является исходным BSL-примером. Он не
  принят запуском в 1С и не является готовым EPF/CFE.
- [Битрикс24, webhook и дайджест](AUTOMATION_RECIPES.md) представлены локальными
  заготовками; реальная внешняя отправка не принята.
- MAX, мини-приложение и цифровой ID требуют самостоятельного подключения.
  Для актуального Bot API используются `platform-api2.max.ru` и заголовок
  `Authorization: <access_token>`; токен в query не поддерживается.
  [Документация MAX](https://dev.max.ru/docs-api).
- Цифровой рубль подключается через соответствующую банковскую инфраструктуру.
  Bell не исполняет платежи; наличие уведомления или ключа ЕПГУ не дает такого
  доступа. [Банк России](https://cbr.ru/faq/dr/).

Уведомление не является достоверным конечным статусом услуги только потому,
что в его тексте есть слово «готово». Base64 сохраняет текст в JSON, но не
шифрует его. Признаки неполного сбора, ошибки сессии и ограничения охвата
должны передаваться получателю вместе с записями.
